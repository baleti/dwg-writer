# DWG format notes (own analysis)
Provenance legend: EXP = found by experiment on corpus files; GEN = general prior knowledge of public format descriptions (no code copied); none taken from ODA/LibreDWG sources.

## R13/R14/R2000 container (AC1012/AC1014/AC1015)
- 0x00 magic(6); 0x0B maintenance byte; 0x0D RL image seeker; 0x13 RS codepage; 0x15 RL locator count; from 0x19 records of 9 bytes: RC number, RL seeker, RL size. [GEN layout, EXP verified on 15/15 files]
- Locator 0 = header variables, 1 = classes, 2 = object map, 3 = unknown (seen 0/0), 4/5 = other (R2000: 4 size 4?, 5 at 0x61). Only 0 and 1 examined so far.
- Sections 0/1: 16-byte start sentinel, RL size, data, RS CRC, 16-byte end sentinel = bitwise complement of start. [EXP: 15/15]
- Start sentinel header vars = cf7b1f23fdde38a95f7c68b84e6d335f, classes = 8da1c4b8c4a9f8c5c0dcf45fe7cfb68a. [EXP]
- CRC: reflected CRC-16 poly 0xA001, seed 0xC0C1, over (size field + data), little-endian stored. [EXP: found by exhaustive seed search on one file, then 15/15 files]

## R2000 object map (locator 2) [GEN layout, EXP verified]
- Chunks: RS size (big-endian, counts size field + pairs), pairs, RS CRC (big-endian, same CRC16/0xC0C1 over size+pairs); size <= 2 ends the map.
- Pair = unsigned modular number (handle delta, 7 bits/byte, 0x80 = more) + signed modular number (offset delta; final byte bit 6 = sign).
- BOTH deltas restart from 0 at every chunk (EXP: keeping either one across chunks desyncs).
- Validation: object at offset = RS size, then BS type, RL bitsize, handle H; the handle equals the map key for 2845/2846, 393/396, 3822/3822, 70/71, 761/761, 1812/1812 entries in the 6 AC1015 files (misses not yet examined).
- AC1012/AC1014 maps: CRCs pass and offsets are in range, but some handles decode huge: R13/R14 handle encoding differs somewhere, not solved (<1% of corpus, deferred).

## Bit reader (dwgbits.py)
- B, BB, BS (00 RS, 01 RC, 10 zero, 11 256), BL (00 RL, 01 RC, 10 zero), BD (00 RD, 01 1.0, 10 0.0), H (4-bit code, 4-bit length, big-endian bytes). [GEN, handle/type fields consistent with map: EXP]

## R2000 entities (dwgobj.decode_entity_r2000) [GEN layout, EXP verified against ODA File Converter DXF output of AC1015_57, used as oracle only]
- Object type codes: 1 TEXT, 17 ARC, 18 CIRCLE, 19 LINE (counts match DXF entity counts). 500+ = class-defined (LWPOLYLINE, HATCH, MTEXT ...) via classes section.
- After handle: EED loop (BS size, H app, bytes), graphic-present B (+RL size, skipped), entmode BB, nreactors BL, nolinks B, color BS, ltscale BD, ltype flags BB, plotstyle flags BB, invisible BS, lineweight RC; then entity data.
- LINE: zflag B, x1 RD, x2 DD, y1 RD, y2 DD, [z1 RD, z2 DD], thickness BT, extrusion BE. DD: BB 00 default, 01 low 4 bytes patched, 10 6 bytes patched (bytes 4,5 then 0-3), 11 RD.
- Oracle check 1: LINE endpoints 252/252 unique segments identical to DXF.
- Classes section (R2000): bit stream of BS num, BS version, TV app, TV cpp, TV dxf, B zombie, BS item id (TV = BS length + bytes). 13 classes parsed in AC1015_57 (500 DICTIONARYWDFLT ... 512). [GEN, EXP]
- Fixed type codes seen: 42 DICTIONARY, 77 LWPOLYLINE, 78 HATCH, 79 XRECORD (counts match DXF 35 LWPOLYLINE in AC1015_57). Class types 500+ via classes.
- TEXT (type 1): dataflags RC, [elev RD], ins 2RD, [align 2DD], ext BE, thick BT, [oblique RD], [rot RD], height RD, [widthf RD], TV, [gen BS], [halign BS], [valign BS]; a flag bit SET means field omitted/default. Oracle check: 207/207 unique (text, x, y, height) identical to DXF.
- LWPOLYLINE (type 77): flag BS (1 normal, 2 thickness, 4 const width, 8 elevation, 16 bulges, 32 widths, 512 closed), then optional fields in that order, numpts BL, [nbulges BL], [nwidths BL], first point 2RD then 2DD relative to previous, bulges BD*n, widths 2BD*n. Oracle: 35/35 (count + first two points).
- LAYER (type 51): object common = EED loop + nreactors BL; then name TV, B, BS, B, flags BS (bit0 frozen, bit2 locked), color BS. Oracle: 12/12 layer names and colours identical to DXF (flag meaning of other bits not yet verified).
- Handle stream (R2000): starts at bit 16+bitsize of the raw object (16 = size field; bitsize = RL after the type). Codes: 2-5 absolute (value = handle), 6 own+1, 8 own-1, 10 own+val, 12 own-val. First code-5 handle of an entity is its layer: resolves to a LAYER object for 100% of 319 LINE/TEXT/ARC/CIRCLE/LWPOLYLINE/INSERT in AC1015_57. INSERT: second code-5 handle = BLOCK_HEADER (type 49) (1/1). A leading (3,0) handle appears on all entities (meaning not determined). [EXP]
- INSERT (type 7): ins 3BD, scale flag BB (00: x RD, y DD(x), z DD(x); 01: x=1, y DD(1), z DD(1); 10: x RD, y=z=x; 11: 1,1,1), rotation BD, extrusion 3BD, has-attribs B. [GEN, decodes plausibly: 1 insert; not yet oracle-compared]

## R2004 family container (AC1018 / AC1024 / AC1027 / AC1032) [GEN layout, EXP verified on 34/34 corpus files]
- Block at 0x80 (0x6C bytes) is XORed with an LCG byte stream (seed 1, state = state*0x343FD + 0x269EC3 mod 2^32, byte = state>>16). Decrypts to 'AcFssFcAJMB\0' in all 34 files.
- Decrypted fields used: 0x54 page map address (+0x100 = file offset), 0x5C section map id. System page: 20-byte header (type 0x41630E3B, decompressed size, compressed size, compression 2, checksum), then LZ77 data.
- Page map: (page id, size) int32 pairs, running address starts at 0x100; negative id = gap (16 extra bytes). Section map page: header 20 bytes, then per section: size Q, page count, max decompressed size 0x7400, ?, compressed flag (2 = LZ77), id, encrypted, 64-byte name, then (page number, size, start offset Q) per page.
- Data page header (32 bytes) XORed with 0x4164536B ^ page address; type 0x4163043B; compressed size at +8. Page placed at the 'start' offset from the section map; decompress to section maxpage size (field 'page size' in the header is not the decompressed length) and truncate to section size.
- LZ77: opcodes written from understanding; EXP corrections: for op 0x10 and 0x12-0x1F offset base is +0x4000 (not +0x4001); 0x12-0x1F match length = (op&15)+3. A wrong offset base raised IndexError on 12/34 files, which exposed the bug; sizes of all sections then match (no page checksums verified yet).
- LZ77 correction (EXP, solved by least squares on per-page output length: every page must decompress to exactly the section page size): opcode 0x12-0x1F match length = (op&15)+2, offset base +0x4000 for 0x10 and 0x12-0x1F. With this every page of AC1018 AcDbObjects ends exactly at the terminator.
- Data page header fields (after XOR): type, section number, compressed size, on-disk page size (compressed+32 aligned), start offset, ?, checksum(?), adler32 of the compressed bytes (field 7: matches, seed 0). Not used by the decoder yet.
- AcDb:Handles (R2004 family) uses the same chunked pair coding as the R2000 object map; offsets are into the decompressed AcDb:AcDbObjects. AC1018 check: object handle at the map offset equals the key for 18465/18466, 87087/87098, 6988/6994 entries (3 files; object header = MS size, BS type, RL bitsize, H handle in AC1018).
- R2010+ (AC1024/1027/1032) object header at the map offset: MS size (2 bytes, extended if bit 15 set), MC handle-stream size in bits, OT object type (BB: 0 RC, 1 RC+0x1F0, 2/3 RS), then H handle. Object handle equals the map key for 3000/3000 sampled entries in one file of each version. [GEN, EXP]

## R2010+ handle stream and string stream (EXP)
- Handle stream start = (size field bytes + MS size)*8 - MC handle-stream size + 8 bits (the naive position is 8 bits early). After the fix the first code-5 handle of LINE/ARC/CIRCLE/LWPOLYLINE/TEXT/INSERT is a LAYER: AC1024_02 17188/17188, AC1027_13 2366/2407, AC1032_07 865/867.
- String stream (R2007+ objects, incl. AC1024/27/32): the bit just before the handle stream is a flag; if 1, the 16 bits before it are the string-stream size in BITS (if bit 15 of that is set, another 16-bit word before it holds the high part), and the string data starts that many bits earlier; strings are TU (BS length in chars, UTF-16LE). Layout: [string data][RS bits][flag][handles]. Oracle: TEXT in AC1027_13: text, x, y, height identical for 56/56. CIRCLE 25/25, ARC 22/22 (AC1027_13); CIRCLE 3/3 (AC1024_02); CIRCLE 99/99, ARC 220/220 (AC1032_00).

## AC1021 (R2007) - work in progress (lz21.py, r21.py); everything below found by experiment on the 8 corpus files
(SUPERSEDED: the grammar notes in the AC1021 sections up to "AC1021 SOLVED" at the end of this file contain wrong rules, e.g. the literal chunk orders and the hi-nibble-0/0xF opcodes; lz2007b.py is the working decoder.)
- Header: 0x80..0x3D8 holds 3 byte-interleaved RS blocks (255 bytes each, 239 data + 16 parity, parity not checked). De-interleave (block j = bytes j, j+3, ...), concatenate data parts: [8 crc][8 key][8 comp-crc][int32 comp len][int32 len2][compressed stream]. Stream decompresses to exactly 0x110 bytes: Q0 = 0x70, Q1 = file size (matches in 8/8 files).
- Literal copy order is NOT sequential: the run is split from the front into 8-byte, 4-byte and single-byte chunks and emitted in reverse chunk order with each chunk kept as is (lz21.RULE 2). Evidence: system header Q fields (Q3 constant 5; page map size = 16 * page count only with this rule), UTF-16 text "AcDb:App" in the section map. COUNTER-EVIDENCE: for a 15-byte run containing UTF-16 text the observed order was [r14 r13][r9..r12][r1..r8][r0] (not the rule's [r14 r13 r12][r8..r11][r0..r7]); the rule for lengths 14+ is therefore wrong or the run boundary differs. Unresolved.
- System header Q fields (R2007): Q0 0x70, Q1 file size, Q2 crc64, Q3 5, Q4 seed, Q7 page map offset (+0x480), Q8 page map id, Q9 header2 offset (+0x480; header2 ends at EOF), Q10/Q11 page map compressed/uncompressed size, Q12 page count, Q13 max page id, Q22/Q25 section map compressed/uncompressed size, Q23/Q24 section map page id and its backup copy. 
- Page map: located at Q7 + 0x480; its RS interleave factor k is not stored (found by trial 4..17); decoded entries (size, id) tile the file from 0x480 (sum of sizes + 0x480 + 0x400 = file size in 8/8 files); negative ids are gaps. Page map pages are k*256 bytes on disk (k blocks of 255 + pad).
- Section map page (ids Q23/Q24) is not yet decodable: the stream decodes to a plausible header and the name text 'AcDb:App...' but the parse stops at stream byte 112 (op 0xF5 with impossible offset). Possible causes: wrong literal ordering for long runs shifting nothing (parse is order independent) so an unknown opcode form is the more likely cause.
- Plan: use the ODA converter as an oracle to write an R2007 DWG from a known R2004 corpus file (ACAD2007 DWG output) and compare section plaintext for ground truth of the literal rule and the unknown forms.
- (AC1021, later) Form 2 (opcode 0x2L, mid-stream): 2 extra bytes, match length = low nibble, offset = b1 + ((b2 & 0xF8) << 1) + 1 (guess, only the length is verified: an ODA-written AC1021 file's section map then parses to exactly the expected 2140 bytes), literals = b2 & 7. Section map RS interleave factor there was 15 (not S/256).
- Literal ordering ground truth from UTF-16 names (3 runs; ODA-written small file and corpus file 7): 13-byte run -> [r12][r8..11][r0..7]; 15-byte run -> [r14][r13][r9..12][r1..8][r0]; 17-byte run -> [r9..16][r8][r0..7] (r = run bytes in stream order). No single chunk rule explains all three yet (see previous note). Preview and other sections of that file have only short literal runs, so they give no new data.
- R2010+ handle stream start (CORRECTION, EXP): (size_field_len + MS size)*8 - handle_bits + 8 * (number of bytes of the MC handle-size field). The earlier fixed +8 was only right when the MC fit one byte. Large objects (BLOCK_HEADER with many owned-entity handles) have 2-3 byte MCs. Block names then decode (AC1027_33: 5 of 6 names equal to the DXF block table; the sixth differs only by naming '*Paper_Space' vs '*Paper_Space0').
- Strings in R2007+ objects: table entry names are in the string stream when its flag is set; the main-data TU is empty (BS length 0) in that case. R2004 (AC1018) names are single-byte in the file codepage (header codepage field), not decoded yet (mojibake for CJK layers in AC1018_42).

## Decoder validation without an oracle: dwgent.expected_end / selfcheck.py (2026-10-17)
- After a decoder reads all fields of an entity, the bit position must equal the end of the main data: the handle stream start (AC1015/AC1018) or the start of the R2007+ string area (hb - 17 - size, or hb - 1 when there is no string stream). ## AC1021 progress notes (2026-10-17, evening) - still unsolved parts marked
- ODA File Converter (oracle only) can write ACAD2007 DWG from corpus R2004/R2015 files: 9 small AC1021 files generated in the scratchpad. Their section map pages are the best study material: the unused data bytes of an RS page are filled by repeating the compressed stream cyclically, so the true compressed length P of a stream = the autocorrelation period of the de-interleaved page data (found P = 832..1304, always about 0.4 * decompressed size). Q22 of the system header is NOT that length.
- Section map RS interleave factor k is not page_size/256 (k=15 for a 4608-byte page, k=18 for another): found by trial (stream must start with 0x20 00 00).
- Parse rules verified so far on those 9 streams (parse reaches the end near P with output close to usz in 6 of 9): hi nibble 0: literal run of (low+8) bytes, low nibble 15: 23 + next byte; F1 (0x1X) and default forms as above; F2 (0x2X) is a long match whose length is NOT the low nibble: the op bytes 2b 08 81 30 (present at output offset ~494 in all 9 streams) must produce a match of 235 bytes (derived from the stream end constraint). Best fitting length formulas so far: lo + 8*b1 + 8*(b2>>3) + 32, or lo + 16*(b2>>3) - 32 with a 4-byte op; unresolved. 
- Literal order rule: run lengths 13, 15, 17 give chunk layouts (compressed order) 8,4,1 / 1,8,4,1,1 / 8,1,8 (unique solutions from known UTF-16 names); no simple rule found yet.

## Writer foundations (2026-10-18) - found by experiment, validated by the ODA converter reading our output
- R2004 header block (0x80, 0x6C bytes, LCG-XOR encrypted): CRC32 (zlib) of the decrypted block with the crc field (0x68) zeroed. Fields: 0x28 last page id, 0x2C end of the last page (rel. to 0x100; = page map address + its LISTED size), 0x34 second header address (absolute), 0x40 number of page map entries, 0x50/0x54 page map id/address(-0x100), 0x5C section map id, 0x60 id array size (= max page id), 0x64 gap array size.
- Data page header (32 bytes, XORed with 0x4164536B ^ page address): type 0x4163043B, section id, compressed size, on-disk page size (aligned 0x20), start offset in section, 0, header checksum, data checksum. Data checksum = adler32 variant (a,b mod 65521, seed 0) of the compressed data; header checksum = same adler over the decrypted 32-byte header with the header-checksum field zero, seed = data checksum.
- System page (page map 0x41630E3B, section map 0x4163003B): 20-byte header (type, decompressed size, compressed size, 2, checksum); checksum = adler(compressed data, seed = adler(header with checksum 0)).
- The file ends with a 20-byte system header (type 0x41630E3B, zeros, 2) plus a second copy of the encrypted 0x6C block; the page map's listed size covers it.
- Preview section (AcDb:Preview, uncompressed): the 0x0D image seeker of the file header = file address of the preview data, and the preview header stores ABSOLUTE file offsets of its images (shift them when the page moves).
- Uncompressed sections (flag 1) hold their data padded to a multiple of 128 in one page; compressed ones use pages of <= 0x7400 bytes.
- A literal-only LZ stream (literal run opcode (+extension) ... bytes ... 0x11) is accepted by both our reader and ODA.
- R2010+ object: the MS size counts the bytes AFTER the MC handle-size field; the CRC16 (seed 0xC0C1) over everything before it follows the data (all 20120/11299/2747 objects of three files verify). R2000/R2004: CRC16 seed 0xC0C1 over size field + data (100% verified).
- Result: dwgwrite.rewrite_r2004(buf) re-emits AC1018 file; ODA converts it to a DXF identical to the original's except timestamps.

### AC1021 LZ, status 2026-10-18 (all found by experiment; oracles: object CRC16, R2004 32-bit window set of the same drawing, exact output length)
- Opcode forms (first byte high nibble): 1 = [op][b1][b2] len=(op&15)+3 off=b1+((b2&0xF8)<<5)+1 lit=b2&7; 2 = 3 bytes, len=(op&7)+(b2>>3) off=b1+1 lit=b2&7 (fits 7 of 9 section map pages, not yet exact on the objects page); 3..15 = [op][b] len=hi off=(op&15)+((b&0xF8)<<1)+1 lit=b&7; 0 = literal run of (op&15)+8 bytes (+next byte if nibble 15) or, rarely, a long match; first byte 0x2? at page start = preamble [20 00 00 xx], xx&7 initial literals.
- Which high-nibble-0 opcodes are literal runs and which long matches is NOT understood: exp/lzdfs.py decides by backtracking (the output must end exactly at the uncompressed size); on the first AcDbObjects page of an ODA-written file it finds a parse (357 literal runs, 6 long matches) and yields 2 objects with valid CRC, the third fails (the F2 op at stream index 248 and/or the parse choice around it).
- Literal copy permutations (exp/permdfs.py: DFS over byte permutations constrained by the R2004 window set). Written as chunk lists in lz2007.py CHUNKS: the literal run is cut into chunks (source order) that are written in reverse order; n>=32: 32-byte blocks (8-byte quarters reversed) then the remainder by the table. Confirmed exact for n=5,6,7,10,14,15,18,19,20,22,23 (several runs each, same permutation); n=4 identity is not confirmed; n=1..3 untested.
- exp/permsolve.py, permagg.py, permdfs.py, localcrc.py, f2crc*.py are the experiment drivers.

### AC1021 breakthroughs, 2026-10-18 (found by experiment; oracle: object CRC16 chain of the first AcDbObjects page of an ODA-written file, R2004 window set, AutoCAD dump)
- RS pages carry 251 data bytes per 255-byte codeword (4 parity bytes), not 239: the LZ stream is the concatenation of raw[j::k][:251] (k=127 for that page). The 239 assumption looked right for the first 239 bytes only, which hid it for a long time (stream byte 239 onward was wrong).
- With 251 the opcode grammar is: hi nibble 1: [op][b1][b2] len=(op&15)+3 off=b1+((b2&0xF8)<<5)+1 lit=b2&7; hi 2: [op][b1][b2] len=(op&7)+(b2>>3) off=b1+1 lit=b2&7; hi 3..15: [op][b] len=hi off=(op&15)+((b&0xF8)<<1)+1 lit=b&7; hi 0: literal run of (op&15)+8 bytes (+next byte if nibble 15), OR a long match [op][b1][b2] len=(op&15)+0x13+((b2>>3)&0x10) off=b1+((b2&0x78)<<5)+1 lit=b2&7 (the choice is not understood: exp/lzdfs2.py decides by backtracking with the object CRC chain as pruning; 20 long-match cases in 29.7 KB).
- Literal copy table (lz2007.CHUNKS, REM for remainders after 32-byte blocks; chunk lists in source order, written in reverse order): n=2 [2], 3 [1,2], 4 [4], 5 [4,1], 6 [1,4,1], 7 [1,4,1,1], 8 [8], 9 [2,3,4], 10 [1,8,1], 11 [1,8,1,1], 12 [8,4], 13 [8,4,1], 14 [1,8,4,1], 15 [1,8,4,1,1], 16 [8,8], 17 [1,8,8], 18 [1,8,8,1], 19 [8,8,1,1,1], 20 [8,8,4], 21 [8,8,4,1], 22 [8,8,4,1,1], 23 [8,8,4,1,1,1], n>=24 8s then 4 then 1s; n>=32: 32-byte blocks with the 8-byte quarters reversed, then the remainder. Entries confirmed by CRC: 1,4-8,10,12-15,18-21,27,29 (and remainders 4,5,6,10,17,29); 2,3,9,17 came from a joint CRC search (one hit, weaker); 11,16,22,23,24-26,28,30,31 are extrapolated.
- Result: the first AcDbObjects page (29.7 KB) decodes with valid CRC for objects from offset 4 up to 24255 (hundreds of objects); handles/types look right (BLOCK_CONTROL 0x1, LAYER_CONTROL 0x2, ...).

### AutoCAD acceptance of rewritten R2004-family files (found with the AutoCAD oracle, 2026-10-18)
The ODA converter accepted our rewrites, AutoCAD (open error 434) did not. Found by bisection (replace one page / one section of an original file at a time):
- Every compressed page stream must end with 0x11 followed by two zero bytes, and the page header's compressed size must be exactly the stream length including those two zeros (page total = align(32 + size, 0x20)).
- Every compressed data page must inflate to the full page size (0x7400) also for the last, partial page: pad with zeros (a long offset-1 match makes this cheap).
- Opcodes 0x18-0x1F do not occur in AutoCAD streams: far matches (offset >= 0x4000) are 0x10 + (cb - 2) for cb 4..9 and 0x10 + rlong(cb - 9) otherwise. The earlier "needs recovery" fixes (page map entry count, id array, preview seeker) remain necessary.
- dwgwrite.lz77_compress is a greedy LZ77 compressor using only forms seen in AutoCAD output; files come out smaller than the originals. exp/wtest.py + exp/acopen.py validate edits with the AutoCAD oracle (modified LINE + cloned LINE correct in AC1018, 1024, 1027, 1032; AC1015 opens too).
MINSERT (type 8): decoder and array expansion added from the public field order; no MINSERT object in the local corpus, so unvalidated (NEEDS a sample from the c6 corpus).

## AC1021 findings from AutoCAD-written specimens (2026-10-18, found by experiment; exp/ac1021-autocad/, c4-dwgwriter, drawing content known)
- Classes page (page id 15 of ac1021_line_text, RS 251 bytes/block, k=5): begins with the public 16-byte classes sentinel; the first 32-byte block is emitted as 8-byte chunks in reverse order (confirms the 32-byte block rule on AutoCAD output). The class-name strings (UTF-16, odd absolute offsets) act as ground truth for literal chunk order.
- Literal chunk order for SHORT runs (after-match literals): n=2 -> [1,1] (stream 00 45 gives 45 00) and n=3 -> [1,1,1] (stream 68 00 74 gives 74 00 68), 6 independent text cases (the earlier table said [2] and [1,2]). With this the class names decode cleanly ("AcDbDictionaryWithDefault", "ACDBPLACEHOLDER", "ObjectDBX Classes", "AcDbTableStyle"). n=5 is [4,1] or [2,2,1] (both fit). 15-byte run confirmed [14][13][9..12][1..8][0].
- Opcode 0xF6 (high nibble 0xF) with bytes 9f 80 behaves as the long match of the hi-nibble-0 form (len = (op&15)+0x13+((b2>>3)&0x10) = 41, off = b1 + ((b2&0x78)<<5) + 1 = 160, literals b2&7): in the section map it reproduces the 160-byte record stride and the names "AcDb:AppInfoHistory", "AcDb:AppInfo", "AcDb:Preview", "AcDb:SummaryInfo". The general match form (len = hi nibble) is therefore NOT used for hi=0xF. Form 1 (hi=1) with the old offset formula b1+((b2&0xF8)<<5) fails inside the section map; the shift 2 variant (b2&0xF8)<<2 lets a beam search reach the end, unverified.
- Section map header fields: q[22] is not a compressed size (values 15893 / 6018 in two specimens), q[25]=0x7f2 (2034) is the uncompressed size; the compressed size is unknown, page = 18 blocks (4608 bytes) twice (ids 18 and 19 = q[24], q[23]).

## R13/R14 (AC1012/AC1014) LINE layout, found by experiment against the AutoCAD dump of AC1012_46 (2026-10-18)
Object = [RS size][BS type (10 bits for 19)][H handle][EED: BS size loop][39 bits, not decoded: varies per object, contains 9 variable bits then 0000000 1 and 16 zero bits then 6 bits][BS colour (CMC is a plain BS here: 256 = ByLayer, verified on 33 samples with 8 colours)][4 bits 0110][LINE data]. LINE data = 3BD start point + 3BD end point with PLAIN BD codes (00 + RD, 01 = 1.0, 10 = 0.0), no z-is-zero flag and no DD compression (all 33 samples reproduce both points exactly). The layer handle sits in the handle area at the end of the object as H code 5 (e.g. 0101 0001 + byte for layer handle 0x76). Not yet decoded: the 39-bit block (entity mode, reactors, ltscale, flags), thickness/extrusion after the end point, the handle order, and every other entity type; tables (LAYER etc.) not looked at.
- (AC1021, later 2026-10-18) KEY RULE found with the classes page of the AutoCAD specimen: a hi-nibble-0 opcode directly after a literal RUN is always the long match (A form); literal runs only follow a match that carried no literals. With this rule plus the short-run chunk orders, the whole classes page (1255 stream bytes) decodes to a clean class list (AcDbDictionaryWithDefault, ACDBPLACEHOLDER, MATERIAL, AcDbMLeaderStyle, CELLSTYLEMAP, AcDbLayerIndex, SPATIAL_INDEX ... with their app names). lz2007.parse implements it. Still open: the section map (page 18/19, 18 RS blocks, usz 2034): names 1-3 decode ("AcDb:AppInfoHistory", "AcDb:AppInfo", "AcDb:Preview") but the 4th ("AcDb:SummaryInfo" at out 516) comes from the ops "f7 08 f7 c3 0d 00 75 00 6d 53 ..." which none of the tried forms reproduce (exp/secmapdfs.py DFS with name constraints dies at out 485); objects pages 10/11 not yet through.
- (AC1021, 2026-10-18 late) VERIFIED on 16 pages: scanning every data page of the 8 local AC1021 files (page map readable, q[7]==0) for the classes sentinel (8d a1 c4 b8 ... 8a) or the header sentinel (cf 7b 1f 23 ... 5f), decoding with lz2007.parse (strict grammar: hi-nibble-0 after a match without literals = literal run, otherwise long match A; hi 1: off = b1 + ((b2 & 0xF8) << 5) + 1; hi 2: ln = (op&7) + (b2>>3), off = b1 + 1, 3 bytes; hi 3..14: ln = hi; hi 15 = A form; chunk orders n=2 [1,1], n=3 [1,1,1]) puts the end sentinel EXACTLY at 16 + 4 + size + 2 for all 8 classes pages and all 8 header pages. So Classes and Header sections of AC1021 are readable (find the page by sentinel, no section map needed). hi2 occurs 8 times and hi 15 27 times in these pages. Not yet reading: the big multi-page classes sections (AC1021_05/10: first page stops at out 6521 with an invalid hi1 offset, probably bit-shifted text hides a mis-parse), Handles, Objects, and the AutoCAD-written section map. Some pages of the specimen (4, 5, 6, 7, 9, 12, 13) are probably stored uncompressed (compression flag in the section map), which is why the LZ parse fails there.
- (AC1021, objects, 2026-10-18 late) Page id 11 of exp/ac1021-autocad/ac1021_line_text.dwg is the FIRST AcDbObjects page (plaintext starts 'ca 0d 00 00' then objects [RS size][data][CRC16 seed 0xC0C1], first object at offset 4). With the strict grammar (bug fixed in my DFS scripts: a hi-0 opcode is a literal run ONLY after a match without literals) exp/lzcrc.py verifies 50 objects by CRC (up to out 3663). Literal chunk order found: n=9 is stream chunks [8,1] (output = last byte first, then the 8-byte chunk), NOT [2,3,4]; n=12,13,14,15,16,18,19,21,29,41,43,52,55,71 are confirmed correct by CRC under the current table. hi-15 opcodes: both the A form and a general match with length 15 (off = (op&15) + ((b1&0xF8)<<1) + 1, literals b1&7) occur; the CRC DFS tries both. The object at out 3663 (size 171) needs n=20, 22, 26 literal orders (unconfirmed; exp/lzcrc.py does a joint search over canonical chunk families). Alignment dependence of the chunk order (stream position mod 8) is still a possibility.

## R13/R14 entities (2026-10-19, found by experiment against existing AutoCAD dumps; no new oracle jobs)
- Entity header is the same for every type: after type BS, H handle, EED loop: 39 bits (undecoded), BS colour (256 = ByLayer), 4 bits, then data. In 26 of ~1000 lines of non-model blocks the header is 18-24 bits shorter (not understood, those entities mis-decode).
- Data uses plain BD (no DD, no z flags, no BT/BE): LINE = BD3 + BD3 + BD thickness + BD3 extrusion; CIRCLE = BD3 centre, BD radius, BD thickness, BD3 ext; ARC adds BD start, BD end angle; POINT = BD3, BD thickness, BD3 ext, BD x-axis angle. Then handles as H: (3 owner/0), (5 layer), then prev/next as relative codes. Layer handle = code 5. Exact on 4 files (LINE 969+3018+4443+1629, ARC, CIRCLE, POINT; layers equal).
- Table objects (LAYER 51, BLOCK_HEADER 49, STYLE 53, LTYPE 57): name = BS length + single-byte chars at 34 bits after the EED loop. BLOCK_HEADER handle list after the name (+16 bits): [4 control][3][5][3 BLOCK entity][4 first entity][4 last entity][3 ENDBLK]; the entities of a block are the handles in [first, last] (verified on SINK1_5B: 79 = 79); model space entities are the rest. Anonymous blocks are stored as '*U'/'*D' without number.
- (AC1021, 2026-10-19) Negative results, so nobody repeats them: (a) no threshold on (b2 & mask) decides between the A form and the length-15 general match for hi-15 opcodes (exp/f15probe.py, 35 rules, none beats trying both with the CRC chain); (b) 84 variants of the hi-1 offset/length formula for b2 >= 0x80 change nothing at the first dead ends; (c) no single match op (length 0-30, offset 1-500) and no permutation of a single literal run (<= 7 bytes) fixes the failing object at out 3838 of ac1021_line_text page 11; (d) the 4-byte MS size form of objects (> 32 KB) must be handled in the CRC chain (done in lz21crc.py). Literal chunk orders now known: n=2 [1,1], 3 [1,1,1], 9 [8,1], 17 [8,1,8], 26 [8,8,1,8,1] (stream order). The dead ends of corpus pages 12/14/05 are parse-level (invalid hi-1 offsets after a hi-15 or hi-3 op), which points to one more unknown opcode form.
- R14 class objects (2026-10-19): the class numbers are per file (LWPOLYLINE 500 in AC1014_44 but 560 in AC1014_37, HATCH 561); the class table is read with dwgobj.parse_classes_r2000. HATCH (class) follows the R2000 layout with plain BD/RD: elevation BD, ext 3BD, pattern name (BS length + bytes), solid B, assoc B, BL paths (flags BL; polyline paths B bulges B closed BL n + 2RD [+BD]; else BL segments with RC type 1 line / 2 arc / 3 ellipse / 4 spline; BL boundary count + handles), style BS, pattern type BS, pattern data, pixel BD when a path has flag 4, BL seeds 2RD. 316 of 322 hatches equal the dump (pattern, solid, loop count).
- R14 orphans (c6): entities whose owner handle (leading handle of the tail) does not exist are not loaded by AutoCAD; *U blocks referenced neither by an INSERT nor by an ACDB_DYNAMICBLOCKPURGEPREVENTER_VERSION object are dropped (all versions).

## AC1021 SOLVED (2026-10-19, c7-dwgparser; found by experiment, checked by object CRC16 chains, corpus object maps and AutoCAD dumps)
Everything below is implemented in lz2007b.py (LZ), r21.py (system header, page map), dwgr21.py (section map, sections), wired into dwgload/dwgmodel.
- LZ grammar (state machine, "chain" = after a match without literals, "top" = after literal bytes): the stream starts with the literal-run state (op 0x0F... = run) or a preamble 0x20 b1 b2 b3 (b1, b2 ignored, b3 & 7 literals follow, then top state). Match forms by high nibble of the opcode: 1: len (op&15)+3, off = b1 + ((b2&0xF8)<<5) + 1, lit = b2&7; 3..15: len = hi, off = (op&15) + ((b1&0xF8)<<1) + 1, lit = b1&7 (one extra byte); 2: off = b1 | b2<<8, len = op&7, then if op&8 == 0: b3, len += b3&0xF8, lit = b3&7, else off += 1, len += b3<<3, b4: len += ((b4&0xF8)<<8) + 0x100, lit = b4&7 (two extra bytes, rare); 0 at "top": A form len = (op&15)+0x13 + ((b2>>3)&0x10), off = b1 + ((b2&0x78)<<5) + 1, lit = b2&7; 0 in a chain: literal run of (op&15)+8 bytes (+ next byte if 15, + 16-bit words while 0xFFFF follows); 0xF? in a chain: the same A form with the nibble masked (the F marks "match" because 0 means literal run there). Literal bytes (after a match, or in a run) are copied permuted: 32-byte blocks as four 8-byte words in reverse order, the remainder and runs < 32 as a chunk list written in reverse order (lz2007.CHUNKS; 24..31: 24 [8,8,8], 25 [8,8,1,8], 26 [8,8,1,8,1], 27 [8,8,1,8,1,1], 28..30 8,8,8,4,1.., 31 [1,1,8,8,8,4,1]; found by trying all chunk compositions against the object CRC).
- RS interleave: data pages use 251 payload bytes of each 255-byte block and k = floor(size/255) blocks; system pages (section map) use 239 bytes per block and an interleave factor k found by trial (the exact output size is the check). Page-map and system header decode with the same LZ (239 bytes per block).
- Section map (page q[24], usz q[25]): records of 8 qwords [data size, max size, encrypted, hash, name length, unknown, encoded (1 plain, 4 compressed), page count] + UTF-16 name + 7-qword page entries [offset in section, max size, page id, usz, csz, checksum, crc]. The pages of a section are in logical order (not file order). A page with csz == usz is stored raw (after RS). Sections with encoded == 1 are plain bytes at the page position.
- Objects: Handles section = object map as in R2000, AcDbObjects offsets index the concatenated pages; object CRC chain verified on all 8 local files (about 200k objects) and 200 of 200 sampled files.
- Class table: size at byte 16, bitsize RL at byte 20 (no extra RL as in AC1024), class bits start at bit 227, strings in the string stream at the end. Header variables start at bit 168. SummaryInfo: 8 strings, each a u16 length (counting the terminating NUL) followed by that many UTF-16 chars.

## ACIS (REGION / 3DSOLID / BODY), 2026-10-19 (found by experiment; checks: AutoCAD dump Area / extents)
- Entity data after the common part: B empty, B unknown, BS version. Version 1 (R2000-R2007): repeated BL block length + that many bytes (every byte > 32 stored as 159 - c) until a zero length = SAT text. Version 2 (R2010+): the SAB binary follows directly (bit-shifted, up to the end of the main data, ends with the record "End-of-ACIS-data"). B empty = 1: no ACIS data.
- SAB: header "ACIS BinaryFile", i32 version/nrec/nent/flags, 3 strings (tag 7), 3 doubles (tag 6); records of tagged values (3/4 int, 6 double, 7 string, 0xA/0xB bool, 0xC pointer, 0xD/0xE identifier, 0x11 end, 0x13 position, 0x14 vector, 0x15 enum); pointers index the record list (asmheader = 0). SAT text: same records in text ("$n" pointer, "@n str", index prefix "-n" only in newer versions; old style (ACIS 4.0) has no id / history fields).
- Topology: body -> lump -> shell -> face(loop, surface) -> loop -> coedge(next, prev, partner, edge, sense) -> edge(vertex, param, vertex, param, curve) -> vertex -> point. Curve parameters: straight-curve p = root + t * dir (t is the length), ellipse-curve angle from the major axis (minor = normal x major * ratio). dwgacis.faces() (planar loops) gives REGION areas equal to the AutoCAD dump within 1e-5 (subtract the first point before the shoelace: coordinates reach 5e10), dwgacis.wire() gives all edges; 3DSOLID/BODY extents equal the dump. Surfaces other than planes (cone, sphere, torus, spline, intcurve edges) are not evaluated yet.

## R2013+ ACIS data store (2026-10-21, c8-dwgparser; found by experiment)
Section AcDb:AcDsPrototype_1b: segments tagged 0xD5AC + 6-char name; '_data_' / 'blob01' segments hold the 'ASM BinaryFile' files (SAB with 'ASM' product, end record End-of-ASM-data, tag 0x0F/0x10 subtype brackets) in file order; rows [u32 0x14, u32 1, u64 handle, u32 offset] in '_data_' segments list the owner objects. ## R12 (AC1009) reader (dwgr12.py, 2026-10-22, c8-dwgparser; equal to the AutoCAD dumps of AC1009_51/_54 per block and type, counts equal on 11 of 17 sampled files, the rest differ only POLYLINE vs LWPOLYLINE naming and 2 files with paper-space VIEWPORTs)
Header: u32 at 0x14/0x18 = main entity stream start/end (model space), 0x1C = start of the block-definition stream (BLOCK .. ENDBLK records up to EOF). Table directory from 0x2C, 10 bytes each [u16 entry size][u16 count][u16 0][u32 start]: 0 BLOCK headers (45 B; flag 128 = erased, no BLOCK record; the others follow the BLOCK records in order; DIM and INSERT block indexes are table indexes), 1 LAYER (41 B), 2 STYLE (198), 3 LTYPE (191), 4 VIEW (153). LAYER entry = [flags][name 32 B NUL padded][ff ff][i16 colour (negative = off)][u16 ltype index][CRC16].
Record = [type][flags][u16 size incl. CRC][u16 layer index][u16 mask of optional fields][u8 colour if flags&1][xdata if flags&0x40 (not for BLOCK/ENDBLK): u16 byte count + items, then 1 extra byte][u16 ltype if flags&2][handle if flags&0x20: count byte + big-endian bytes][data][CRC16]. In the block stream this header is not always parsed the same way, so fixed-size data is located from the CRC (size from type and mask) and text data by fitting the string lengths. Types: 1 LINE 2 POINT 3 CIRCLE 7 TEXT 8 ARC 11 SOLID 12 BLOCK 13 ENDBLK 14 INSERT 15 ATTDEF 16 ATTRIB 17 SEQEND 19 POLYLINE 20 VERTEX 23 DIM. Plain little-endian doubles.
- LINE: flags&4 = 2D (x1 y1 x2 y2), else 6 doubles. CIRCLE cx cy r. ARC cx cy r a0 a1 (radians). SOLID 4 x (x,y) in storage order. POINT x y.
- TEXT: x y height, u16 length + chars, then by mask bit: 0x01 rotation, 0x02 width factor, 0x04 oblique, 0x08 style index (1 byte), 0x10 generation, 0x20 horizontal alignment (1 byte), 0x40 alignment point (2 doubles; equals the insertion point when not justified, AutoCAD recomputes the position), 0x100 vertical alignment byte. ATTRIB/ATTDEF: x y height, text, [ATTDEF prompt], tag (u16 length strings), 1 flag byte (1 invisible, 2 constant, 4 verify), then the TEXT fields with (mask >> 1).
- INSERT: data = u16 block table index, x, y, then by mask 0x01 sx, 0x02 sy, 0x04 rotation, 0x08 sz (this order, defaults 1), 0x100 extrusion (3 doubles; (0,0,-1) mirrors x). DIM: data starts with the u16 index of its picture block.
- POLYLINE: mask 0x01 flag byte (bit 1 closed), 0x02 start width, 0x04 end width, 0x100 u16 curve type. VERTEX: x y, then 0x01 start width, 0x02 end width, 0x04 bulge, 0x08 flag byte. SEQEND ends the vertex list.
Not read: linetype/style/dimstyle tables (colours by layer only), header variables, extended data content, 3DFACE/3DLINE/TRACE/SHAPE (types seen in no sample).

## R13/R14 common entity header (found 2026-10-22, c8-dwgparser, experiment against AutoCAD dumps)
After [RS size][BS type][H handle][EED]: [B graphic flag (1: RL byte count + that many bytes)][RL bit size of the entity data][BB entmode][BL number of reactors][B isbylayerlt][B nolinks][BS colour][BD ltype scale][BS invisibility] (45 bits for defaults), then the entity data. entmode 2 = model space, 1 = paper space, 0 = owned by the block given by the first handle (relative codes 6/8/10/12 = h +1/-1/+v/-v); nolinks = 1 means the entity has no prev/next handles. dwgr14._entmode reads it: it equals AutoCAD's space for every LINE of 6 R13/R14 files (about 190,000 entities: model 2, paper 1, blocks 0); the former first/last handle walk wrongly put thousands of model entities into paper space in AEC files (AC1014_06: paper 3408 -> 514 entities, AutoCAD 517).
Open: in AC1014_06 some *D picture blocks are merged (entities of several blocks share the same relative owner offset); handle values in the block headers (0x253d...) and in the entities (0xfe31...) live in different 64-bit spaces.
- R13/R14 header, bits between the two BL and LTSCALE (claude8, 2026-10-23, exp/r14hdrflags.py, found by experiment): gaps of 266..346 bits in the 9 corpus files; for every (n B, m BS) split no single pair lands on the LTSCALE position in more than 4 of 9 files (best (16,33), (22,42), (26,40)), so this part is not a fixed run of single bits then BS values (variable-length codes or other fields in between). LUNITS and friends stay undecoded for R13/R14 (units only; the viewer does not need them).
